# How to Contribute to Component Viewer?

**First of all:** If you think about contributing by submitting a pull request, please take the `dev` branch as your base branch. This is where all contributions usually get merged into. It reflects ongoing development for the latest Minecraft and mod version.

## Reporting Bugs / Suggesting Features and Changes

1. Take a look at the issues page if someone already reported the same bug or suggested the same feature
2. **If so:** You can show your interest in it getting fixed or implemented there (e.g. by reacting or replying with additional information)
3. **If not:** Create an issue describing the bug (as detailed as possible) or the feature you wanna see

## Fixing Bugs / Implementing Features / Changing Behaviour

1. If you don't have a bug or feature you wanna fix/implement, you can take a look at the issues page for open issues that aren't already assigned to anyone
2. **For bugs:** If the bug you wanna fix only affects an older version of Minecraft, it's certainly best to create an issue for it first, because merging into the `dev` branch is impossible for most of these bugs
3. **For features and behaviour:** It's best creating an issue for it first, to refine and discuss how it fits the mod's vision and style
4. Take a look at the current code to better understand styling conventions of this mod (this is to avoid unnecessary re-formatting)
5. Go ahead by submitting a pull request targeting the `dev` branch

## Writing Documentation

1. You can freely add, tweak or fix documentation for public fields, methods and classes (private, package-private or protected fields, methods and classes should only be documented if necessary for understanding the code)
2. Take a look at current documentation to better understand how it's written and formatted
3. Do not use `@author` tags, since contributions are solely determined by git commits
4. Go ahead by submitting a pull request targeting the `dev` branch

## Translating

1. You can freely add, tweak or correct translations (no matter which language, although `en_us` is the baseline and should only be rephrased or corrected)
2. When creating the JSON file(s), take the `en_us.json` file as the baseline and make sure all translation keys are in lexicographical order
3. Go ahead by submitting a pull request with the JSON file(s) targeting the `dev` branch
